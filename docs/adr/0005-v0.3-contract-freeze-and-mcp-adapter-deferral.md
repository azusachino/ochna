# ADR-0005: v0.3 contract freeze and MCP adapter deferral

Status: Accepted
Date: 2026-07-29

## Context

v0.3 turned ochna from a fast symbol-lookup index into a diff-aware
structural review tool (`doctor`, `unresolved`, `tests-for`, `impact`,
`diff`). A review-oriented tool needs its command surface and JSON
envelopes to be something callers (human or agent) can build against without
the ground shifting underneath them — but ochna was also still evolving
quickly (confidence-tiered resolution landed in the same cycle, ADR-0001).

Separately, a read-only MCP adapter was drafted as design material: a
no-write, no-shell, no-network wrapper mapping MCP tools 1:1 onto the
existing `--json` CLI contracts (`ochna_status` → `status --json`,
`ochna_diff` → `diff --json`, etc.), with per-tool workspace allow-listing.

## Decision

Freeze the v0.3 command surface and JSON envelopes as a versioned contract
(`docs/v0.3-contract.md`): a later task may add fields, but may not rename,
remove, or change the meaning of a field or human-visible section without a
new contract version. Every new v0.3 command's JSON output carries
`contract_version: "0.3"` for exactly this reason.

Defer the MCP adapter rather than build it speculatively. The installed CLI
plus its stable JSON contracts already cover the read-only automation
surface (an agent can shell out to `ochna --json <cmd>` directly); no
concrete MCP-only consumer, discovery/allow-list requirement, or
persistent-service need was demonstrated. The adapter's design (frozen in
`docs/v0.3-contract.md`'s "Read-only MCP adapter (deferred)" section) is
kept as ready-to-build material, not implemented. Reopen only against a
concrete MCP-only requirement — tracked as
[issue #9](https://github.com/azusachino/ochna/issues/9) in the v0.4
milestone.

## Consequences

- `docs/v0.3-contract.md` is the canonical spec other docs point at rather
  than duplicate (`scripts/verify_clis.py`'s acceptance tests,
  `scripts/case_simulation.py`'s corpus-benchmark cases, and this ADR set
  all reference it instead of re-stating its contents).
- Any future MCP work has a frozen starting design instead of needing to be
  designed from scratch, but ships nothing until a real consumer exists.
- Contract violations (renaming/removing a field without a version bump)
  are a compatibility break, not a routine change — they need their own ADR
  and a new `contract_version`.

## Alternatives considered

- Building the MCP adapter alongside v0.3 — rejected: no demonstrated
  consumer, and the CLI's own `--json` contracts already serve the same
  read-only automation need without adding a second server process/allow-
  list surface to maintain.
- Leaving the v0.3 surface unversioned/informally stable — rejected: a
  review tool that agents and CI gate on needs an explicit compatibility
  promise, not an implicit one.
