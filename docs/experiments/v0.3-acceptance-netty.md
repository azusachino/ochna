# v0.3 Acceptance — Netty Corpus Benchmark

This experiment runs the frozen `docs/v0.3-contract.md` acceptance scenario
for the Netty corpus: `doctor`, `callers --show-resolution`, `tests-for`, and
`impact --direction callers` against the pinned commit, plus a manual
`rg`-based comparison for the same question. The submodule at
`clones/netty` was never `cd`-ed into, indexed, or mutated; the pinned tree
was archived read-only into a temporary directory that was deleted at the
end of the run.

  `TrafficShapingHandlerTest::testQueuedWritesReleasedAndFailedOnClose`

## Required evidence: pass/fail

### 1. `ochna callers releaseAndFailQueuedWrite --show-resolution --json`

**Real time: 0.01s.** Returned exactly the three expected callers, each
`resolution_kind: "package"`, `confidence: 80`:

- `io.netty.handler.traffic::ChannelTrafficShapingHandler::handlerRemoved`
- `io.netty.handler.traffic::GlobalChannelTrafficShapingHandler::handlerRemoved`
- `io.netty.handler.traffic::GlobalTrafficShapingHandler::handlerRemoved`

**PASS** — matches the contract's required evidence exactly, no extra
noise, no missing caller.

### 2. `ochna impact releaseAndFailQueuedWrite --direction callers --json`

**Real time: 0.04s.** Default `--depth 2`, `--min-confidence 30`. `nodes`
contains the same three `handlerRemoved` methods; `edges` contains the
three `calls` edges at confidence 80; `paths` preserves one root-to-node
path per caller (`p1`, `p2`, `p3`); `affected_tests` is empty (consistent
with the `tests-for` result below); `unresolved_boundaries` lists the
ambiguous/missing call sites at each `handlerRemoved` frontier (e.g.
`isActive`, `write`, `isEmpty`, `ClosedChannelException`, `clear`,
`hashCode`) rather than silently traversing through them. `truncated:
false`.

**PASS** — impact traversal reproduces the same three-caller blast radius
as `callers`, with confidence and unresolved-boundary bookkeeping intact.

### 3. `ochna tests-for releaseAndFailQueuedWrite --json` — confirmed blind spot

**Real time: 1.21s.** The target resolves correctly
(`AbstractTrafficShapingHandler::releaseAndFailQueuedWrite`,
`handler/src/main/java/io/netty/handler/traffic/AbstractTrafficShapingHandler.java:586`),
but `data.tests` is an **empty array**. `ok: true` (a zero-result query is
still a successful, honest answer per the command contract).

This confirms the previously identified blind spot still holds on this
pinned commit: `ochna node --symbol testQueuedWritesReleasedAndFailedOnClose
--include-code --json` shows the real `@Test` method
(`testQueuedWritesReleasedAndFailedOnClose`) delegates to a private
package-scoped helper,
`testQueuedWritesReleasedAndFailedOnClose0(AbstractTrafficShapingHandler
trafficHandler)`, which exercises `handlerRemoved` indirectly (via pipeline
removal / channel close), not through a direct call to
`releaseAndFailQueuedWrite`. There is no structural `calls` edge from the
test to the target helper, so `tests-for` correctly and honestly reports
no direct-call evidence rather than inflating the result with a
same-module or name-based guess.

**Documented blind spot, not a regression to fix**: `tests-for` will always
return empty for production symbols whose only test coverage is indirect
(lifecycle-triggered rather than directly invoked). This is the project's
explicit, deliberate tradeoff — keep `tests-for` honest over inflating it
with an unproven lifecycle heuristic — and this run reconfirms the
behavior is unchanged on the pinned Netty commit. No source change was
made or attempted.

## Manual `rg` comparison

```bash
time rg -n "releaseAndFailQueuedWrite" --type java
# real 0.10s (0.03 user, 0.49 sys — dominated by ripgrep's own startup/threading)
handler/.../AbstractTrafficShapingHandler.java:586:    static void releaseAndFailQueuedWrite(...)
handler/.../GlobalChannelTrafficShapingHandler.java:502:  releaseAndFailQueuedWrite(toSend.toSend, toSend.promise, cause);
handler/.../GlobalTrafficShapingHandler.java:283:         releaseAndFailQueuedWrite(toSend.toSend, toSend.promise, cause);
handler/.../ChannelTrafficShapingHandler.java:154:        releaseAndFailQueuedWrite(toSend.toSend, toSend.promise, cause);

time rg -n "handlerRemoved" -g '*TrafficShapingHandler*.java'
# real 0.03s
# 8 lines across 4 files: each handler's own handlerRemoved override plus its super.handlerRemoved(ctx) call
```

**Signal/noise comparison:**

- `rg releaseAndFailQueuedWrite` is fast (~0.1s) and, for this
  *specific, distinctively-named* symbol, happens to return exactly the
  definition plus its 3 call sites — text search got lucky here because
  the name is unique in the codebase. It required no prior knowledge of
  which class the calls live in.
- `rg handlerRemoved -g '*TrafficShapingHandler*'` is faster (~0.03s) but
  returns 8 raw lines (definition + `super.handlerRemoved` call, per file)
  with no indication of which lines are overrides, which call the shared
  helper, or how they relate to `releaseAndFailQueuedWrite` at all — a
  human still has to open each file and read the method body to confirm
  the caller relationship. `rg` cannot answer "does this override call the
  helper" or "what confidence does that call have" the way
  `ochna callers --show-resolution` does in one 0.01s structured call.
  `handlerRemoved` is also a common Netty method name (`ChannelHandler`
  lifecycle callback), so an unscoped `rg -n "handlerRemoved" --type java`
  would return calls across the entire codebase, not just the traffic
  package — `ochna callers` avoids that fan-out entirely because it
  resolves the graph edge, not the substring.
- Net comparison: `rg` is marginally faster wall-clock for a single
  distinctive literal, but `ochna callers`/`impact` deliver the
  relationship (who calls whom, at what confidence, with what unresolved
  boundaries) directly as structured data; `rg` only ever delivers text
  matches that still require manual correlation. For the `tests-for`
  question specifically, `rg` also cannot express "no direct structural
  call exists" — it would just show the indirect-usage lines and leave the
  absence-of-a-direct-edge judgment to the human, whereas `ochna tests-for`
  states that absence explicitly via an empty, honest result.
